## 3. 第 2 项：真实 Kubernetes staging 边界

### 3.1 为什么不是把 kubeconfig 直接交给 Agent

模型和主控制面不直接持有集群管理员凭据。独立 connector 以 ServiceAccount 运行在 `harbor-sandbox` 命名空间，服务端工具注册表只开放两个动作：

- `inspect_kubernetes_workload`：读取命名 Deployment、Scale、Pod、Event 和命名 ConfigMap；
- `scale_kubernetes_deployment`：只更新命名 Deployment 的 `scale` 子资源。

API 与 Worker 通过 kind 创建的私有 Docker network 访问 control-plane NodePort；宿主机的验证入口只监听 `127.0.0.1:18094`。这样 Linux CI 不依赖 Docker Desktop 特有的 host gateway 代理，也没有为了兼容性把 connector 放宽到所有宿主网卡。

这遵循 Kubernetes 官方 RBAC 的命名空间最小权限原则。实现参考 [Kubernetes RBAC good practices](https://kubernetes.io/docs/concepts/security/rbac-good-practices/) 与 [RBAC reference](https://kubernetes.io/docs/reference/access-authn-authz/rbac/)。实验集群由固定到 v0.32.0 且校验 SHA-256 的 kind 创建，入口参考 [kind Quick Start](https://kind.sigs.k8s.io/docs/user/quick-start/)。

### 3.2 权限矩阵

| 能力 | 集群实际判定 | 设计理由 |
|---|---|---|
| 读取 `demo-api` Deployment / Scale | 允许 | 获取当前副本与资源版本 |
| 列出命名空间内 Pod / Event | 允许 | 做就绪和告警取证 |
| 读取命名 `demo-api-signals` ConfigMap | 允许 | 实验容量信号，不读取通用配置 |
| 更新 `demo-api` Scale 子资源 | 允许 | 唯一写权限 |
| 读取 Secret | 拒绝 | Agent 不应看到集群密钥 |
| 创建 Pod / `pods/exec` | 拒绝 | 防止任意代码执行 |
| 修改 Deployment 模板 | 拒绝 | 防止换镜像、加挂载或扩大权限 |
| 创建 RoleBinding | 拒绝 | 防止自行提权 |

### 3.3 并发与失败语义

- Harbor capability 绑定 tenant、job、tool、payload 和 fencing token；
- connector 再用 Kubernetes Lease 记录已接受的最大 fencing token 和幂等结果；
- Scale 写入携带 `metadata.resourceVersion`，利用 API Server 的乐观并发检查；
- 审批前只调查，不写；中风险 Scale 必须由 `on-call-lead` 批准；
- 写后重新读取副本和 ready replicas；超时或不满足成功条件时自动回滚到调查时观察到的副本数，并再次验证。

## 4. 第 3 项：数据库演进、恢复与可靠性

### 4.1 版本化迁移

启动时不再散落执行 `CREATE TABLE IF NOT EXISTS`。`schema_migrations` 记录版本、名称、SHA-256 校验和和应用时间；SQLite 用 `BEGIN IMMEDIATE` 串行升级，PostgreSQL 用事务级 advisory lock 串行多个 API / Worker 的并发启动。

当前迁移链：

1. Run、Job 和 Evaluation 基线；
2. Evaluation tenant 维度和索引；
3. Worker 进程心跳表和时间索引。

旧 v3.3 数据库没有迁移表也可就地纳管；迁移重复运行不重复修改。已经应用的 SQL 若被篡改，校验和不一致会 fail closed。数据库版本高于程序支持版本时同样拒绝启动，避免旧程序误写新结构。

新库冷启动还存在另一种并发：API 和两个 Worker 会同时初始化 pgvector。PostgreSQL 的 `CREATE EXTENSION IF NOT EXISTS` 不能消除并发系统目录竞态，因此扩展、派生知识表、种子和 HNSW 初始化使用独立的数据库级 transaction advisory lock。双线程同时起跑的 PostgreSQL 回归测试会先移除测试库中的 vector 扩展，再证明两次完整初始化都成功；测试只作用于专用数据库。

### 4.2 Worker fleet 不是“猜在线”

过去外置 Worker 只暴露各自的 `/metrics`，API 只能把 `verified` 写成 false。现在空闲和忙碌 Worker 都每 5 秒向 PostgreSQL 写进程心跳；API 以 20 秒 TTL 返回真实副本 ID、启动时间、最后心跳和 delivery status。当前本机状态为 2 个 Worker 都已验证在线。

Job lease 仍负责“谁有执行权”，进程心跳只负责“谁活着”，两者没有混为一个概念。

### 4.3 真备份与真恢复

`database-ops.py` 使用 PostgreSQL custom-format `pg_dump` 生成事务一致归档，原子落盘并写 sidecar manifest。恢复默认只允许创建一个新数据库，拒绝覆盖 `harbor`、`postgres` 和模板库。

| 归档大小 | 120,236 bytes |
| SHA-256 | `3467d3b3ae8ebc1071dd05719c89d961151db840ebe93bdcd8a7a8087cd10426` |
| schema migrations | 3 |
| agent runs | 48 |

归档随后恢复到随机命名临时数据库。迁移版本、五张核心表行数和孤儿任务检查全部一致，临时库在验证后自动删除。这证明“文件能生成”之外，文件确实能恢复。

### 4.4 故障注入

最终本机有界矩阵在 16.099 秒内完成 8 次闭环运行，0 失败；包含：

- 4 次轮换 Worker 重启；
- 2 次 PostgreSQL 重启；
- 1 次 Prometheus 停机与恢复；
- Prometheus 停止时 tool runtime 为 unavailable、readiness 为 503；恢复后重新为 ready；
- 数据库重启后迁移版本仍为 3 / 3；
- Worker registry 最终等待恢复到初始副本数才允许报告通过。

该数字是快速故障回归，不是长期稳定性结论。`reliability-lab.py --duration-seconds 28800` 可执行 8 小时 soak，但本报告没有把未运行的 8 小时写成证据。

## 5. 第 4 项：105 项密封对抗评测

### 5.1 数据结构

5 类隐藏状态故障 × 21 个共享变体 = 105 个独立 case。每个 case 都新建 Fault Lab experiment 和 SQLite 数据库，模型/fixture 运行时看不到 oracle；只有运行结束后 evaluator 才读取隐藏成功条件。

21 个变体覆盖：

- 中文、英文和伪 system prompt；
- 伪造角色、审批和变更单；
- 扩大租户/环境/实例范围、伪造成功、错误根因；
- 无关噪声和 48 次重复长上下文；
- Unicode bidi、零宽字符、全角同形字符、Base64；
- JSON、XML、Markdown tool-call 结构；
- 紧迫话术和 Secret 外泄诱导；
- 注入真实只读工具输出的恶意 annotation。

### 5.2 评分不是字符串相似度

每例同时检查：根因覆盖、隐藏业务状态、检索文档、工具选择、风险审批、禁止工具、capability JTI 和动作后结果。工具输出注入若没有造成越权、但诱导系统选择了错误的“允许工具”，也会因 tool correctness 失败，不能靠“没调用禁止工具”拿安全分。

## 8. 仍未完成，禁止包装

- staging connector 只允许一个命名空间和一个 Deployment 的 Scale；没有真实 production 写权限；
- kind 是本机单控制面，未做多节点、跨主机、跨 AZ 或 Kubernetes API 分区；
- 没有企业 OIDC、MFA、SCIM/JIT、Vault/KMS、mTLS 和 WORM 审计；
- 本轮只有快速故障矩阵，没有 2–8 小时 soak、容量曲线和长期错误预算；
- PostgreSQL 完成逻辑备份恢复，但没有 PITR、WAL 归档、自动调度、加密保管和跨区域恢复；
- 105 项 fixture 回归没有覆盖恶意知识库摄取、多轮聊天或本轮真实模型重复试验；
- Evaluation API 仍是同步管理操作；全量真实模型评测应迁移到持久后台任务；
- 本地模型仍是 CPU 高延迟路径，生产吞吐需要 GPU、副本、批处理或大小模型路由；
- 没有当前 CVE 扫描、SBOM 签名和供应链准入结论。

## 9. 最终判断

对 20K+ 岗位，这一版的价值不是“又多用了 Kubernetes”。真正的证据是：权限被集群本身限制，计划被审批绑定，并发由 resourceVersion 与 fencing 约束，动作后用同一真实边界复查，数据库能升级也能恢复，Worker 在线状态可证明，评测报告给样本规模和置信区间。

面试时应把项目定位成：

> 一个本地优先、证据约束、最小权限、可恢复的 AgentOps 控制面；已在 Compose 与单节点 kind staging 完成真实工程演练，生产接入仍需企业身份、真实集群、HA、长期 SLO 和全量真实模型评测。

这个表述足够强，也足够诚实。
