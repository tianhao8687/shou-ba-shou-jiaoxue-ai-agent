## 4. 问题清单

### P0-1（已完成）：Run 状态与 Job 入队不是一个事务

**证据**

`start()`、最终审批和失败重试都分别调用 `save_run()` 与 `enqueue_job()`。

**风险**

进程在两次提交之间崩溃时，Run 已显示 `queued`，但没有可领取 Job，用户会看到一个永远不再推进的运行。

**整改**

- 新增 Store 级 `save_run_and_enqueue()` 原子操作；
- SQLite 与 PostgreSQL 都在同一事务内完成 CAS 保存和 Job 创建；
- 为同一 Run + stage 的活动 Job 增加去重约束；
- 增加 orphan reconciler 修复旧数据和异常中断遗留记录。

**验收**

- 人工制造 Job INSERT 失败时，Run 保存必须同时回滚；
- 重复提交相同 stage 只能存在一个 queued / claimed Job；
- orphan Run 能被修复，终态和 `awaiting_approval` 不得被错误入队。

### P0-2（已完成）：租约丢失不会及时停止正在运行的模型或工具

**证据**

Heartbeat 线程只设置本地事件，Agent 收到的是不含动态失效状态的静态 `LeaseContext`；只有 `engine.process()` 返回后 Worker 才检查 `lease_lost`。

**风险**

数据库暂时不可用或租约被新 Worker 接管时，旧 Worker 仍可能继续调用外部工具。当前 Fault Lab 的幂等能减轻问题，但未来真实 Kubernetes、云 API 或数据库连接器不能只依赖进程内判断。

**整改**

- `LeaseContext` 增加动态取消事件与 `assert_active()`；
- 每个节点、每次模型调用、每次工具调用和验证读取前后检查租约；
- 连续 heartbeat 异常超过安全预算时主动失效，不等待数据库明确返回 stale；
- fencing token 进入远程工具请求与持久执行记录；
- 工具服务拒绝低于已观察 token 的旧请求。

**验收**

- 慢工具运行期间丢失 lease，旧 Worker 不得开始下一次副作用；
- stale fencing token 即使 capability 与幂等键有效，也必须被工具服务拒绝；
- heartbeat 数据库异常不能无限继续执行。

### P0-3（已完成只读部分）：普通生产事件没有真实观测能力

**证据**

没有 `experiment_id` 的事件在 investigate 节点直接转人工；本次浏览器实测为 0 observation、0 model call。

**风险**

当前闭环能力只适用于 5 类 Sealed Fault Lab 故障，不能证明 Agent 能处理陌生生产事故。

**整改**

- 引入独立的只读 Observability Provider 接口；
- 首个生产适配器连接 Prometheus HTTP API；
- 支持配置化 service label 和查询模板；
- 只在取得可归因证据时调用模型；
- 未配置写执行器时只能生成诊断与建议，必须转人工，绝不复用实验工具伪造生产执行。

**验收**

- 对真实 Prometheus 中存在的服务取得带来源 URI 的 Observation；
- 空数据、超时、认证失败均 fail closed；
- production 事件不得携带 Fault Lab oracle 或实验工具能力令牌；
- 未配置生产写执行器时，不产生写副作用。

### P0-4（已完成）：健康与就绪语义失真

**证据**

- Backend `/api/health` 总是返回顶层 `ok`；
- Compose 使用该接口作为健康门；
- 本地模型未加载时 `/health` 已返回 `ready`。

**风险**

编排系统可能把模型不可用、工具不可用或 Worker 不可用的实例继续放入流量。

**整改**

- 区分 liveness、readiness 与诊断详情；
- `/api/health` 只表达进程存活；
- `/api/ready` 根据配置判断数据库、检索、工具、模型以及 API 队列接收条件；内嵌 Worker 模式才直接检查 Worker 线程；
- 外置 Worker 模式下，API readiness 只表达“可安全写入持久队列”；Worker 进程存活由独立容器健康检查和 Prometheus 负责，诊断响应明确返回 `verified=false`，不伪装成整套任务交付 SLO；
- 本地模型未加载时返回 `configured`，只有完成加载后才是 `ready`；
- Compose 改用 readiness。

**验收**

- live-model 模式下模型未加载或不可达，readiness 返回 503；
- fixture 模式明确返回 `fixture`，不得伪装成真实模型 ready；
- liveness 不因外部依赖短暂失败而重启进程。

### P1-1（部分完成）：模型网关不具备成熟在线服务能力

整改前问题包括：

- 收到 `response_format=json_schema` 但没有执行约束解码；
- token 使用字符数估算；
- 推理串行且没有有界队列、排队超时、取消与背压；
- `ThreadingHTTPServer` 缺少生产服务生命周期管理；
- 同步评测请求可能占用连接数十分钟。

本轮已完成：

- 网关拒绝不支持的 `response_format`，健康接口明确声明 `prompt + upstream Pydantic`，不再伪装 constrained decoding；
- 增加单执行槽、有界 admission queue、排队超时、`Retry-After`、429/503 和 active / queued / reject / timeout 指标；

仍未完成：

- 将评测改为异步任务与轮询结果；
- 记录真实 tokenizer usage；
- 研究 OpenVINO 支持的受约束生成后再升级能力声明。

### P1-2：评测规模不足以支持生产准确率结论

当前只有 5 个基础故障、15 个展开变体；提示注入主要来自用户事件文本，未覆盖工具输出注入、长上下文、多轮诱导和编码扰动。

整改方向：

- 最少 100 个隔离案例；
- 每个案例进行多次真实模型重复试验；
- 增加工具输出注入、恶意知识库、Unicode、超长上下文、超时和模型修复失败；
- 增加网络分区、响应丢失、Worker 崩溃、DB 重连和补偿失败；
- 报告置信区间，禁止只报单次百分比。

### P1-3：检索的实际规划贡献被限制

默认 Embedding 是 lexical feature hashing；同时 Diagnose 只把 `routed` 和 `pinned` 来源交给模型，普通 hybrid 命中只展示在 UI，不参与规划。

整改方向：

- 明确 baseline 与 semantic 两种运行档位；
- 通过受控重排和文档 ACL 选择可进入模型的 hybrid 结果；
- 增加增量摄取、版本、租户 ACL、过期检测和离线检索回归。

### P1-4（部分完成）：数据模型和租户隔离不适合扩展

整改前问题包括：

- Run 整体作为 JSONB 存储；
- `list_runs()` 读取全部数据后在 Python 过滤 tenant 和 limit；
- Evaluation report 没有 tenant 维度；
- 启动时 `CREATE TABLE IF NOT EXISTS`，没有 schema migration 版本。

本轮已完成：

- `list_runs()` 的 tenant filter 与 limit 下推到 SQLite / PostgreSQL，并建立 tenant + updated_at 表达式索引；
- Evaluation report 增加 `tenant_id`，保存、latest、metrics 和 API 查询按 tenant 隔离；

仍未完成：

- 提取 `tenant_id`、status、时间和常用查询字段；
- 游标分页和按状态的复合索引；
- 引入版本化 migration，并增加升级/回滚测试。

### P1-5：身份与运维仍是演示级

当前使用固定演示账号、统一密码和默认签名密钥；缺少 OIDC、MFA、密钥轮换、吊销、登录限流、审计导出、备份恢复和跨主机演练。

这些能力需要真实部署环境和身份提供商。本地版本应先做到：

- 非 demo 模式禁止默认密钥启动；
- 登录失败限流；
- signing key id 与轮换窗口；
- 备份/恢复演练脚本；
- OpenTelemetry trace 与告警规则。

### P1-6（本轮范围已完成）：前端测试集中在组件层

整改前只有 16 项组件测试，缺少真实浏览器与可访问性门，而且大量次要文字只有 7–9px。现已增加 Playwright + Axe，在桌面 Chromium 与 Pixel 7 上覆盖登录、键盘焦点、水平溢出、production 只读取证、低风险闭环和高风险双主体 quorum；文本下限和低对比状态色也已修正。断网恢复、证据下载内容校验和长时间轮询仍可继续扩展。
