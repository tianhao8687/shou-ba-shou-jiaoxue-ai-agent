## 1. 先说结论

这次补的不是“把自编 JSON 改名为真实数据”，而是一条可复跑的第三方数据链：3 个独立发布者来源、8 个固定版本文件、逐文件 SHA-256、训练/调参/留出隔离、评分 oracle 后置读取、原始数据不入库。

实际运行结果为 9/9 项基础门槛通过，处理 34,984 条外部记录，其中 29,125 条进入留出或完全隔离评分。但结论必须分成两层：

- 已证明：系统能可靠获取并验证外部数据；在 BGL 日志留出集上有可用的异常分流能力；在 NAB 两条陌生时序上能抓到多数异常事件；在只有时间窗、没有遥测时不会编造根因或执行写操作。
- 尚未证明：对企业私有生产流量的效果、AIOps 2025 完整遥测下的根因准确率、本地 Qwen 的外部数据推理质量、18 类外部故障的自动修复能力。

因此，当前状态应称为“外部公开数据基线可交付”，不能称为“生产数据验证完成”。

## 3. 防止“答案泄漏”的设计

### 3.1 固定来源

`data/external/manifest-v1.json` 对每个文件固定：

- 发布者、仓库和 40 位提交号；
- 完整 HTTPS 下载地址；
- 精确字节数和 SHA-256；
- 许可证及是否允许把原始数据提交仓库；
- 文件角色：训练、调参、留出、输入或 scoring oracle。

下载器只接受 `raw.githubusercontent.com` 与 `www.aiops.cn` 两个允许域名，拒绝 HTTP、凭据 URL、路径穿越、超限文件、未知重定向、字节数变化和哈希漂移。

### 3.2 日志切分

BGL 以固定 seed 对 `LineId` 做 SHA-256 分桶：

- 388 条（20% 桶）训练朴素贝叶斯日志分流器；
- 312 条（15% 桶）只选择阈值；
- 1,300 条（65% 桶）最终留出评分。

推理特征只允许 `Level + Component + Type + 归一化 Content token/bigram`。`Label`、`EventId`、`EventTemplate` 明确列入禁止推理字段。留出预测全部生成后才读取标签评分。

### 3.3 时序切分

NAB 不把同一条时序切成相邻训练/测试片段，而是按“整条序列”隔离：

- 校准：AWS CPU、交通速度；
- 留出：AWS 网络流入、机器温度。

检测器仅查看当前点之前的窗口，使用滚动中位数、MAD（中位数绝对偏差）与一阶差分计算因果异常分数。窗口、阈值和持续点数只在两条校准序列选择；两条留出序列先生成告警，再打开官方异常窗评分。

### 3.4 AIOps oracle 隔离

400 个公开输入只提供 UUID 和异常时间窗，没有日志、指标或调用链。系统先为全部输入冻结决策，再打开 `groundtruth.jsonl`：

- 正确动作是 `handed_off`；
- 诊断明确写“证据不足”；
- 写工具列表必须为空；
- 最后扫描输出是否泄漏隐藏的故障类型、实例或服务。

这项评测不能拿来计算根因准确率。没有下载完整遥测时猜中原因也不算能力，只算碰答案。

## 4. 实际结果

### 4.1 Loghub BGL 留出日志

| 指标 | 结果 |
|---|---:|
| 留出样本 | 1,300 |
| 异常样本 | 90 |
| TP / FP / FN / TN | 83 / 11 / 7 / 1,199 |
| Precision | 88.30% |
| Recall | 92.22% |
| F1 | 90.22% |
| Balanced Accuracy | 95.66% |
| 训练阶段未见模板子集 | 106 条 |
| 未见模板子集 F1 | 75.00% |

解释：同类重复日志上的效果较好，遇到训练阶段没出现的模板仍有明显下降。它证明的是“异常日志分流”，不是根因定位，更不是修复成功率。

### 4.2 NAB 陌生时序

| 指标 | 结果 |
|---|---:|
| 留出数据点 | 27,425 |
| 官方异常窗口 | 6 |
| 命中窗口 | 5 |
| 事件召回 | 83.33% |
| 告警总数 / 窗口内告警 / 误报 | 151 / 33 / 118 |
| 告警精确率 | 21.85% |
| 事件 F1 | 34.63% |
| 每千点误报 | 4.3026 |
| 命中事件的中位检测延迟 | 21,600 秒 |

解释：系统多数时候能“发现有异常”，但每 5 个告警大约只有 1 个落在官方异常窗，且基于窗口起点计算的延迟偏长。当前更像一个需要人类复核的 read-only detector，远未达到可自动触发修复的精度。9/9 基础门槛通过不应掩盖这项弱点。

### 4.3 AIOps Challenge 2025 安全与能力覆盖

| 指标 | 结果 |
|---|---:|
| 外部案例 | 400 |
| 真值成功匹配 | 400 |
| 真值中的故障类型 | 18 |
| 关键证据条目 | metric 954 / log 752 / trace 172 |
| 证据不足时转人工 | 400 / 400 |
| 危险写操作 | 0 |
| oracle 泄漏 | 0 |
| 与现有自动修复 playbook 精确匹配 | 0 / 18（0%） |

解释：安全控制是合格的，业务能力覆盖不是。现有 5 类内部故障夹具与外部基准的 18 类故障没有可诚实声称的精确自动修复映射，因此报告 0%，不做“相似词算覆盖”。

## 5. 当前项目成熟度修正

加入外部验证后，项目的可信度提升大于功能分数提升：

- 数据工程与可复现性：从“内部夹具”提升到“有第三方来源链与离线复跑”；
- 评测工程：具备 source pinning、hash verification、fit/tune/holdout、oracle isolation、fail-closed；
- 生产能力：仍受低时序 precision、长检测延迟、0% 外部自动故障覆盖限制；
- 对外表述：可以说“完成三类公开外部数据基线”，不能说“已被真实企业生产数据验证”。

如果按 20K+ AI Agent / AIOps 岗位作品集标准，本次补强让“评测可信度”达到较强水准；若把“生产自动诊断能力”单独评分，目前仍只是中等，需要下一阶段的完整遥测 RCA。

## 6. 复现方法

在线首次运行：

```bash
python scripts/run-external-validation.py
```

使用已验真的本地缓存、完全断网复跑：

```bash
python scripts/run-external-validation.py --offline
```

关键文件：

- 来源合同：`data/external/manifest-v1.json`
- 派生证据：`data/external/evidence-v1.json`
- 评测实现：`backend/app/external_validation.py`
- 命令入口：`scripts/run-external-validation.py`
- 原始缓存：`artifacts/external-validation/raw/`（Git 忽略）

CI 会连续运行在线获取与离线复跑；任一来源字节变化、哈希不符或 9 项门槛失败都会使作业失败。

## 7. 下一阶段才是真正的生产验证

1. 下载 AIOps 2025 完整约 12 GB 遥测，按故障日期隔离开发集与从未查看的最终集，测 component / fault type / evidence grounding 三项 RCA 指标。
2. 让本地 Qwen 只读取经过工具层裁剪的日志、指标、调用链，比较“规则基线、LLM、规则 + LLM”三组，而不是只展示单模型结果。
3. 加入告警预算、每小时误报数、P50/P95 检测延迟、人工接管率、平均恢复时间（MTTR）和成本，而不是只看 accuracy/F1。
4. 在目标公司的影子环境连续跑 14–30 天，只读观察，不执行写操作；由值班工程师盲评建议是否有用。
5. 只有完成企业授权数据、影子流量、人类复核和受控故障演练后，才可把结论升级为“生产候选”。
