# Harbor AgentOps v3.6 生产加固整改报告

验证日期：2026-08-12

整改分支：`agent/v3.3-production-hardening`

结论口径：经过完整本地生产化测试的 AgentOps 工程原型；不是已经承载企业生产流量的生产系统。

## 1. 结论

本轮没有扩充业务功能，重点修复了四条正确性与安全主线：Docker Runtime 配置依赖、审批到执行之间的状态漂移、多步骤部分失败，以及非演示环境使用默认密钥。PostgreSQL 改用官方 `psycopg_pool`，并保留同一连接内加锁/解锁的 advisory lock 语义。

本地完整验收已通过：后端 131/131、前端 21/21、浏览器 22/22、标准 Compose 双 Worker、Kind 真实 Scale、PostgreSQL 隔离恢复、固定外部数据在线/离线重放和依赖故障矩阵均通过。远端 CI 状态必须以本分支推送后的最新 GitHub Actions 为准；在全绿前不写“6/6 passed”。

## 3. Fresh Observation 与写入顺序

当前写操作顺序为：

`审批/计划哈希/角色 → Fresh Observation → 前置条件重验 → lease/fencing → 动作 capability → 工具写入`

执行前观测使用单独的短效只读 capability，但不复用普通工具幂等缓存。观测失败或字段类型不合法时，不读取旧 Observation 兜底；Run 分别记录 `PRE_EXECUTION_OBSERVATION_FAILED` 或 `PRE_EXECUTION_OBSERVATION_INVALID` 并转人工。状态已经变化时记录 `PRECONDITION_CHANGED`。

审计事件包括 `precondition.revalidation.*`、`precondition.changed`、`tool.execution.*` 和 `compensation.*`。每条事件带 Run、Job、Step、Tool、Actor、Tenant、Plan Hash、Idempotency Key、Fencing Token 和事件时间；不写入完整 token、API key、密码或签名密钥。

## 4. Saga 与结果语义

- `succeeded/skipped`：只代表该动作有确定结果；可补偿工具的逆操作进入 `ready`。
- 后续动作明确 `failed`：只逆序补偿此前确定成功的写操作，补偿后必须走独立只读验证。
- `unknown`：不推断成功或失败，不换幂等键，不重试，不补偿，直接冻结并人工对账。
- 补偿失败或补偿验证失败：`manual_intervention_required=true`，Run 为 `HANDED_OFF`，不伪装成恢复成功。
- 只读步骤不进入补偿集合；没有确定逆操作的写工具继续使用人工恢复边界。

当前自动 Saga 仅对白名单中的 `scale_workers` 和 kind staging `scale_kubernetes_deployment` 生效。逆操作参数来自写前真实副本数，不由 LLM 生成。

## 6. 已解决问题

- Docker missing config：已解决，并由 runtime 容器契约测试证明。
- TOCTOU：已解决写工具在审批后沿用旧状态的问题；失败路径 fail closed。
- Partial Failure：已为可确定逆操作的 Scale 工具补齐持久 Saga；未知结果保持人工对账。
- Production Secret：已解决非演示/production 使用明显默认密钥仍启动的问题。
- PostgreSQL Pool：已接入官方连接池，并保护同连接 advisory lock 语义。

## 7. 未解决问题与技术债

- Run、Observation、Execution、Audit 和 Compensation 仍主要聚合在 `agent_runs.payload` JSONB；这适合本轮小步加固，但高规模查询、冷热分层和审计保留最终需要独立表与迁移方案。
- Unknown Outcome 目前只冻结并人工核对；还没有面向所有外部系统的“按原幂等键查询结果”与自动 reconciliation 协议。
- 自动补偿只覆盖两个 Scale 工具。重启、凭据轮换和缓存刷新没有被包装成虚假的通用逆操作。
- 只有逻辑备份/隔离恢复；没有 WAL/PITR、跨主机 PostgreSQL HA、跨区域恢复演练。
- 当前故障矩阵是分钟级有界实验，不是 8 小时以上 soak，也没有多主机网络分区与容量极限数据。
- 本地演示身份不是企业 OIDC/SSO/SCIM；审计不是 WORM；密钥仍未接 Vault/KMS，服务间也未完成 mTLS。
- 普通 production connector 仍为 Prometheus 只读；真实 Kubernetes 写入只存在隔离 Kind staging，未接企业生产集群。
- Windows 中文路径当前依赖 Docker classic builder fallback；Docker 后续移除 legacy builder 前，应迁移到不受 header 限制的 BuildKit 版本或 ASCII 临时 context。
- 尚未完成已登录漏洞数据库上的持续 SBOM/CVE 扫描、签名镜像和发布证明。
- 公开数据、Fault Lab 和 Kind staging 都不是目标企业 14–30 天影子流量，不能推出生产准确率、SLO 或业务 MTTR。

## 8. Production Boundary

| 层级 | 本轮真正验证了什么 | 不能声称什么 |
|---|---|---|
| production-like | 非 root/受限容器、PostgreSQL、双 Worker、lease/fencing、连接池、审批、能力令牌、幂等、Fresh Observation、Saga、备份恢复、故障注入 | 已在企业生产长期稳定运行 |
| 真实外部系统 | 固定第三方公开数据字节、真实 PostgreSQL、真实 Chromium、真实 Kind API/RBAC/Scale | 目标公司私有事故准确率或生产自动修复率 |
| staging | Kind 命名空间中的受限 Scale 写入与 4/4 Ready 独立验证 | 企业生产 Kubernetes 权限与变更流程已接入 |
| fault lab | 可持久、可故障注入的远程工具服务及副作用/幂等 oracle | 故障实验结果等同真实生产流量 |
| fixture | 确定性 Agent 编排和安全回归 | 真实 LLM 的业务增量价值 |

准确表述是：Harbor AgentOps v3.6 是一个经过完整本地测试、外部数据验证和生产化加固的 AgentOps 系统原型；它具备可信的正确性与故障边界证据，但仍需企业身份、密钥基础设施、生产 connector、长周期影子流量和多主机恢复演练，才能进入真实生产候选阶段。

## 9. Release Evidence 规则

`scripts/generate-release-evidence.py` 读取 GitHub Actions API，只接受 workflow 结论为 success 且六个必需 Job 全为 success 的 Run。任一 Job 缺失、失败、取消或仍在运行，脚本都会拒绝生成 `docs/release-evidence-v3.6.json`，因此不会手写绿色结果。
