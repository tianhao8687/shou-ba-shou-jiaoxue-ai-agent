## 1. 为什么要保留这份问题账本

一个项目最后“能跑”并不能说明开发过程合理。真正能体现工程能力的是：哪里失败过、为什么失败、修复是否触及根因、怎样防止复发，以及还有哪些问题没有资格写成“已解决”。

本文把问题分成四种：

- **实测故障**：测试、浏览器、容器、数据库或真实数据运行时确实失败过。
- **审计缺口**：代码检查已经证明存在风险，但未必等到真实事故才修。
- **方向纠偏**：需求、场景、教学或报告方法一度偏离最终目标。
- **能力边界**：当前实现没有证明，必须继续保留为待办，不能用文案掩盖。

状态含义：

- **已解决**：实现已修改，并有回归测试或机器证据。
- **部分解决**：安全边界已经建立，但生产能力或通用性仍不完整。
- **未解决**：当前仍是明确缺口。

“全部”指截至 2026-08-13 能从 Git 历史、源码、测试、机器证据、整改报告和需求复盘中追溯的问题。没有落盘的临时终端噪声不冒充可审计事实。

本次共整理 **83 条**可追溯问题：72 条已解决或已建立明确工程结论，5 条部分解决，5 条未解决，另有 1 条已经打开答案、不可逆地失去盲测资格，但已被正确标界而没有伪装成新盲测。

## 8. 最值得复用的十条工程教训

1. **模型只负责不确定推理，权限和执行不变量必须由代码控制。** 339 秒大 Schema 失败不仅是性能问题，也是职责划分错误。
2. **“失败”和“结果未知”不是一回事。** 明确失败可以按合同补偿；Unknown 必须冻结并按原幂等键对账。
3. **状态与触发任务要原子发布。** 否则 UI 的 queued 可能只是一个没有 Job 的死状态。
4. **lease 解决临时所有权，fencing 解决旧所有者复活。** 只做 heartbeat 不能阻止过期 Worker 写入。
5. **审批不是永久通行证。** 计划哈希、版本和写前 Fresh Observation 必须在真正执行时再次成立。
6. **工具返回 200 不等于业务恢复。** 必须从独立观测通道验证成功条件，失败时再补偿和复验。
7. **`IF NOT EXISTS`、稳定排序和连接池都隐藏并发语义。** 单进程测试通过不能证明多副本冷启动正确。
8. **评测集通过不等于评测程序可信。** 数据血缘、oracle 隔离、预测冻结、确定性重放和失败账本同样是产品代码。
9. **真实外部数据的价值常常是暴露坏消息。** 21.85% precision 和 0% playbook 覆盖比内部 100 分更能决定权限边界。
10. **文档、隐私和 CI 也需要自动化不变量。** 一份旧报告、一个个人路径或一个历史绿色状态都能破坏交付可信度。

## 9. 当前仍未解决的优先级清单

这些不是“以后再优化”的装饰项，而是阻止项目被称为企业生产系统的真实边界。

### P0：进入企业生产候选前必须完成

1. 企业 OIDC/SSO/MFA、SCIM/JIT、账号吊销和真实职责目录；
2. Vault/KMS、密钥轮换、mTLS 与不可篡改审计存储；
3. 目标企业授权的只读影子流量和 14–30 天人工盲评；
4. 生产 connector 的最小权限、幂等、fencing、对账和变更流程；
5. Unknown Outcome 的通用“按原幂等键查询真实结果”协议。

### P1：可靠性与性能

1. 2–8 小时以上 soak、容量曲线、P95/P99、错误预算和资源泄漏；
2. PostgreSQL WAL/PITR、跨主机 HA、故障转移和跨区域恢复；
3. 多节点 Kubernetes、API Server 分区和跨主机网络故障；
4. GPU/多副本/批处理或大小模型路由，替代一分钟级 CPU 单例；
5. Run、Observation、Execution、Audit、Compensation 从大 JSONB 拆成可查询生命周期表。

### P2：评测、供应链与外部复核

1. 真实 LLM 与 Rule/Workflow 的独立 A/B，证明或否定 LLM 增量价值；
2. 改善外部时序 precision，并把未知故障按“只读识别/建议/受控执行”分级；
3. 正式外部新手、后端/SRE 和面试官三类真人评审；
4. 持续 SBOM/CVE、镜像签名、来源证明和发布准入；
5. 替换 Windows 中文路径下的 legacy builder workaround。

## 10. 怎样用这份文档准备面试

不要背完整清单。任选三条问题，按下面五步回答：

1. 先说用户或生产影响；
2. 说触发问题的真实场景；
3. 解释根因，不只报错误信息；
4. 说明修复建立了什么不变量；
